# 无服务器博客搭建记（1/7）：让飞书文档变成博客

## 一、这期解决什么问题

我想在飞书里写文章，读者在 lizizai.xyz 上看到它，中间不经过任何一台我自己管理的服务器。复制粘贴太蠢，WordPress 后台太难用，本地写 Markdown 又要手动 commit。这期讲整条链路的鸟瞰：一篇飞书文档，怎么变成读者浏览器里的网页。

## 二、背景

### 我的博客是什么

lizizai.xyz 是一个中文技术博客，技术栈是 Next.js 16（一个 React 全栈框架）加一堆 Cloudflare 和 Vercel 的托管服务。支持中英双语，一篇文章可以有文字、播客、幻灯片、交互 HTML 四种形态，还带评论、点赞、浏览量。

听起来东西不少，但整套系统里没有一台服务器归我管。没有 VPS，没有数据库实例，没有 Nginx 配置文件。我甚至连"服务器密码"这种东西都没有。

### 写作和发布为什么总是割裂

写博客的人大多卡在同一个地方：写作体验和发布体验不可兼得。

在 WordPress 后台的编辑器里写作，体验像在政务网站上填一张申报表。换到本地用顺手的编辑器写 Markdown，写得爽了，发布却变成了体力活：保存、commit、push、等构建，写错一个字也要走一遍完整流程。

我想要的状态很朴素：写作发生在写作工具里，发布自动发生。飞书是我每天真正在用的文档工具，协作、评论、版本历史都是现成的，那能不能就让文章"长"在飞书里？

### 一天的真实写作流程

现在我的一天是这样的。早上在通勤路上想到一个选题，打开飞书 App 建个文档写两段；到公司用电脑接着写，顺手 @ 同事帮我看一段表述；晚上把文档挪进博客对应的分类文件夹，完事。

没有"发布"这个动作。我睡觉的时候，同步流程自己会跑，第二天早上文章就在网站上了。写作工具该有的东西——评论、划线、历史版本、多人协作——飞书全都有，我不用为博客单独发明任何一套。

### 这个系列会讲什么

这是《无服务器博客搭建记》的第 1 期，一共 7 期。这期把整条链路铺开看个全貌；接下来的几期，每期拆一个局部讲透：同步器怎么做增量、一篇文章的四种形态、评论点赞怎么不碰数据库、渲染性能怎么优化、构建为什么总是失败，最后一期复盘一次停更一个月的静默故障。

每一期的素材都来自这个真实在跑的仓库，踩过的坑比顺利的决策多，我觉得坑更值得讲。

## 三、别人是怎么做的

这个需求不新鲜，成熟方案有一排。我认真考察过的几类，落到具体行为上是这样的：

| 维度 | WordPress / Ghost（自托管） | Hugo / Astro + Git（纯静态） | 我们的方案（飞书 + 无服务器） |
|------|-----------|-----------|-----------|
| 服务器 | 要一台 VPS 跑 PHP/Node + MySQL | 不需要，产物是纯静态文件 | 不需要，全部是托管服务 |
| 写作环境 | 自家后台编辑器 | 本地编辑器写 Markdown | 飞书文档 |
| 发布动作 | 后台点"发布"即生效 | commit + push 触发构建 | 什么都不做，等定时同步 |
| 日常运维 | 升级、备份、防攻击都要管 | 只管 Git 仓库 | 没有可运维的东西 |
| 数据在哪 | 自己的数据库 | 自己的 Git 仓库 | 飞书 + 自己的 R2 存储 |

除了这两类，还有两条路我也试过或看过。

### 两条没走通的路

一条是 NotionNext、Super.so 这类"文档即发布"产品，思路和我想做的一样：在 Notion 里写，自动变成网站。问题是它们把整个站押在单一平台的 API 上，Notion 的 API 有限流，加载慢了你没办法，数据导出也不算痛快。我在国内，飞书比 Notion 顺手，这是我选飞书而不是 Notion 的全部理由。

另一条是 headless CMS（无头内容管理系统：只有后台和 API、不带页面的内容系统），比如 Strapi、Contentful。这条路人模狗样很专业，我和它的故事放到第 5 章讲——我最初选的其实就是它。

### 一个共同点

把这几类摆在一起会发现一个共同点：它们都在"写作在哪发生"和"发布要不要动手"之间做了妥协。要么写作环境凑合换发布省事，要么写作舒服换发布动手。我不想妥协，只好自己拼一条链路。

## 四、我们是怎么做的

### 先把角色认全

整条链路可以想成一家报社：

- **飞书是编辑部**。文章在这里写、在这里改，协作评论都在这。
- **GitHub Actions 是取稿快递员**（GitHub 的 CI 服务：按时间表或触发条件在云端跑脚本）。每天早上定时去编辑部，把有变化的稿件取回来。
- **Cloudflare R2 是仓库**（对象存储：按 key 存文件，按量付费）。稿件存成 JSON 和 Markdown，还有一个总目录 articles.json。
- **Vercel 是印刷厂**。它托管我的 Next.js 站点，构建时从仓库拉内容印成页面，并用 ISR（增量静态再生：页面印好后被缓存，过期后后台重新印）保证读者拿到的总是较新的一版。
- **四个边缘服务是读者服务台**：点赞、评论、浏览量、访问分析，读者在浏览器里直接和它们打交道，不经过印刷厂。

### 数据流向

```mermaid
flowchart LR
  A[飞书文档<br>编辑部] -- 每日定时取稿 --> B[GitHub Actions<br>取稿快递员]
  B -- 转存 Markdown 与图片 --> C[Cloudflare R2<br>仓库]
  C -- 构建时拉取内容 --> D[Next.js on Vercel<br>印刷厂]
  D -- ISR 缓存页面 --> E[读者浏览器]
  E -- 点赞/评论/浏览量 --> F[边缘服务<br>读者服务台]
```

只看这张图就能复述整条链路：内容从飞书出来，经 GitHub Actions 进 R2，Vercel 构建时读 R2 生成页面，读者访问页面；互动数据则走浏览器旁边的边缘服务，和内容链路互不干扰。

### 快递员的上班时间

快递员每天几点上门，写在一份 workflow 配置里：

```yaml
# .github/workflows/feishu-sync.yml（截短）
on:
  schedule:
    - cron: '0 1 * * *'   # UTC 01:00 = 北京时间 09:00
  workflow_dispatch:      # 手动触发，应急用
    inputs:
      force_sync:
        description: '强制全量同步'
        type: boolean
```

`cron: '0 1 * * *'` 就是每天北京时间早上九点跑一次同步。`workflow_dispatch` 留了一个手动按钮：等不及的时候，我可以在 GitHub 网页上点一下，或者跑一句 `gh workflow run feishu-sync.yml`，快递员立刻出门。

顺带一提，快递员最早不是这位。同步任务起初挂在 Cloudflare Worker 的定时触发器上，后来才搬到 GitHub Actions。Worker 的运行时适合轻快的请求响应，跑这种要装依赖、要压图片的重活束手束脚；GitHub Actions 给的是一台完整的 Linux 机器，pnpm install 装什么都能跑，出错还有完整的日志和重跑按钮。搬家之后，Worker 里的同步代码还留着，只是定时器关了。

同步完成后，workflow 还会调一下站点的 `/api/revalidate` 接口，让 Vercel 把 ISR 缓存清掉，新文章秒级可见；这步失败也不阻塞，缓存一小时后自己也会过期。

### 仓库里到底存了什么

R2 这个仓库里的货物结构很简单。根部一个 `articles.json`，是全站文章的总索引，列表页、分类页、RSS 都靠它。每篇文章一个目录，里面是 `meta.json`（标题、摘要、封面、有哪些内容类型）加 `content.md`（正文），图片和播客音频这类资源文件放在旁边的子目录里。

这些文件通过一个公开的 CDN 地址暴露出来。也就是说，仓库的门永远开着，印刷厂和读者的浏览器都能直接来取货，不需要仓库管理员在场。

## 五、为什么这么选

### 我最初选的其实是 Strapi

得坦白：这个架构不是一步到位想出来的，是删出来的。

项目最早是 Strapi 加本地 MDX。仓库里曾经躺着 `scripts/migrate-strapi-to-mdx.ts` 和 `lib/content.ts` 这样的文件，现在全删了，只剩 git 历史能考古。删掉的原因很实际：一个人维护的博客，Strapi 太重了。我要为它管一台服务器、一个数据库，定期升级，担心备份。而它给我的写作后台，还不如我每天免费用的飞书顺手。

### 两头都要的代价

第 3 章的对比表里，WordPress 和 Strapi 这类方案共同的死穴是"要养一台服务器"。养服务器对团队是小事，对个人爱好项目是持续的注意力泄漏。Hugo 那条路服务器是省了，但发布动作（commit、push）混进了写作心流，我写公众号式随笔时根本不想碰终端。

飞书方案把这两头都占了：写作在飞书，发布零动作。代价也实实在在——文章同时存活在飞书和 R2 两处，得靠同步器保持一致；发布不是即时的，有小时级延迟。这笔账我算过：个人博客晚一小时上线，没有任何人会受伤。

### 调试链路变长了

还有一个更隐蔽的代价：文章没按预期出现时，我要依次排查：飞书里放对文件夹了吗、Actions 跑了吗、R2 里有了吗、ISR 缓存清了吗。环节多，每一环都是别人的服务，能看日志但没法登上去翻。好在每一环都有观测入口，摸清各家的日志在哪看之后，排查并不算痛苦。

### 成本结构

整套链路的月账单是零。GitHub Actions 对公开仓库不限分钟数；R2 有免费额度，个人博客的存储量塞不满；Vercel 的 hobby 档免费；四个边缘服务跑在 Cloudflare Workers 免费额度里。对个人项目来说，"免费额度内能跑"和"免费"基本是一回事。

当然，"免费"是有条件的：我的流量得一直留在各家的免费额度里。哪天博客火了，最先撑不住的大概率是 Vercel 的流量档。到时候再付钱，我心甘情愿——那说明文章真的有人在看。

## 六、踩过的坑

### GitHub 的 cron 不守时

`0 1 * * *` 写的是九点，但 GitHub Actions 的定时任务在高峰期会排队，实际触发常常滞后，官方文档也不保证准点。我的观察是滞后几十分钟到数小时都算正常。

所以 workflow_dispatch 那个手动按钮不是摆设，是必需品。有次我早上发了篇蹭热点的文章，等到中午还没上线，从此记住了：急稿一律手动触发，定时任务只兜底。

### 读者看不到新文章

还有次同步明明成功了，网站首页却没有新文章。查了才发现是 ISR 缓存：Vercel 把页面印好后缓存一小时，同步完成不会自动让旧页面失效。

修法就是前面说的 revalidate 接口，同步成功后主动清缓存。这也是"托管"的另一面：缓存策略是平台的行为，你得读懂它，才能驾驭它。

### 飞书图片链接会过期

早期版本偷懒，正文里的图片直接引用飞书的临时链接。文章发出去当天好好的，过两天图全裂了——飞书的直链有时效，不是给外部网站当图床用的。

所以同步器现在会把正文里每张图都下载下来，转存到 R2 仓库，正文里的地址改写成仓库的 CDN 地址。这也是同步一篇文章比想象中慢的原因之一：图多的文章，光搬图就要搬好一会儿。

## 七、小结与下期预告

回顾这期的要点：

- 写作体验和发布体验可以兼得，前提是把它们拆给不同的工具：飞书管写，流水线管发。
- 整条链路五个角色：编辑部（飞书）、快递员（GitHub Actions）、仓库（R2）、印刷厂（Vercel）、读者服务台（边缘服务），没有一台服务器归我管。
- 这个架构是删出来的，Strapi 的遗迹提醒我：个人项目的第一敌人是运维负担。
- 成本为零，代价是小时级延迟和数据两处存放。

下一期讲这条链路里最硬核的一段：博客有 163 篇文章，快递员每天怎么知道哪几篇改过、只取这几篇？答案是给每篇文章记一笔"高水位"的检查点，以及一个让我栽过跟头的 mtime 陷阱。
